# Explicit viewing privacy and HTTPS GeoIP

Status: planning only. Implementation has not started. Reviewed against main `b066ba7` and the linked primary provider documentation on 2026-10-09. Product choices below remain proposals to review before implementation.

## Current exposure

Management mutations require the administrator token, but monitoring GETs are public. Those responses include individual peer addresses and locations, ban records, RPC endpoints, and filesystem paths. Administrator authentication and Origin validation are separate protections; an Origin check does not authenticate a viewer. The system stream uses a separate response path and needs the same access policy as ordinary routes, even though the current dashboard obtains metrics through its existing info poll and does not consume that stream.

Database-only GeoIP mode suppresses peer provider lookups; it does not prohibit Google reachability probes, GitHub update checks, or dataset downloads. Disabling the GeoIP database is also not a general outbound-network policy.

The current provider URL uses HTTP. The [ip-api free JSON documentation](https://ip-api.com/docs/api:json) states that its free endpoint lacks HTTPS, limits clients to 45 requests per minute per IP, and excludes commercial use. It documents `X-Rl`/`X-Ttl` quota headers and a paid service for HTTPS. These are provider terms and capabilities, not a finding about how a particular operator uses this repository.

## Current-code evidence

- `src/server/app.ts`: administrator checks cover API POST routes. GET and normalized HEAD routes are public, including `/api/peers` with and without `include_status`, `/api/info`, `/api/bans`, `/api/config`, `/api/rpc-info`, and `/api/stats`. `/api/stream/system` responds before ordinary route dispatch; it emits system metrics rather than peers. Generic unhandled HTTP errors already return a fixed message, but explicitly returned service errors and raw node extensions still need field review.
- `src/server/runtime.ts`, `services/connectivity.ts`, `services/updates.ts`, and `services/geoip.ts`: startup can initiate Google probes, GitHub release checks, and dataset downloads independently of the peer-lookup preference. Dataset updates have automatic and manual entry points. The database-only setter changes a boolean; it does not cancel a request already in flight.
- `services/peers.ts`, `services/geoip.ts`, and `services/geoip-schema.ts`: provider observations and persistence currently assume `ip_api` provenance. Missing `mobile`/`proxy`/`hosting` values become false; `src/static/js/distribution/data.js` can then classify a known-AS peer as residential. A provider lacking these fields cannot simply inherit those defaults.
- `src/server/admin-auth.ts` and `trusted-proxies.ts`: validation before anonymous throttling and explicit trusted-proxy identity are already implemented. Viewing authentication must preserve those safeguards rather than depend on a future throttling PR.

## Proposed viewing modes

- Offer deployment-selected public, authenticated, and redacted modes. In public mode, anonymous clients retain the full monitoring view. In authenticated mode, anonymous clients get only the shell/bootstrap/health allowlist. In redacted mode, anonymous clients additionally get the approved aggregate view; authenticated viewers and administrators get the detailed view. Proposed migration behavior preserves existing explicit public configurations; the behavior of older configurations without a mode and new-installation defaults needs a decision before implementation.
- Use a separate viewing credential. A viewer may read protected monitoring data but cannot manage peers or alter settings. A valid administrator credential may also read the full view; management still requires administrator authorization and Origin checks.
- Keep the anonymous shell, local assets, minimal access-mode bootstrap, and minimal `/healthz` liveness response available. Bootstrap must contain no node details or credentials. Static API documentation and schema may remain public if they contain no deployment data; interactive documentation must obey the same protected-read policy. In authenticated mode, start detailed polling only after successful viewing authentication.
- Keep browser credentials in memory, never URL parameters or browser storage. Add bearer support to protected reads. If the browser later consumes the system stream, use an authenticated fetch stream rather than putting a bearer token into an EventSource URL. Clear retained responses and rendered private data when locking, and cancel polls/streams on lock, authentication failure, and reload.
- Apply access checks centrally before route work, sensitive response headers, HEAD/conditional responses, errors, and the direct stream path. No route alias, query option, raw RPC field, or stream may bypass the chosen policy. Protected and credential-bearing responses must be private/no-store, with appropriate `Vary: Authorization` handling; neither shared caches nor a 304 response may serve a previous authenticated representation to an anonymous request.
- In redacted mode, provide a dedicated server-side aggregate response and public UI. Protect the original detailed endpoints, including both peer response forms, bans, config/rpc-info, and streams. Do not fetch full data and merely hide it in the browser.
- Build redacted output from an explicit allowlist: no individual peer identifiers or endpoints, precise locations, ban records, node/proxy endpoints, filesystem paths, provider credentials, raw provider/RPC extensions, or unsanitized errors.
- Proposed initial public information is aggregate peer counts by network/direction plus coarse availability. Do not expose individual map points or table rows. Exact counts over time, especially groups with one peer, can still reveal connection changes; redaction is not an anonymity guarantee. Decide whether to bucket or suppress small groups before approving the aggregate allowlist. Country, AS/provider breakdowns, timing, and error text require separate approval rather than inheriting the existing dashboard payload.
- Validate credential requirements at startup and fail closed for selected private modes with no usable viewing/admin credential. Define a viewing-verification route separately from management authorization so a viewer can authenticate without gaining mutation access. Reuse constant-time comparisons and validation before anonymous throttling, and require explicit trusted-proxy configuration before trusting forwarded identities.
- Proposed initial credentials are operator-configured shared viewing/admin secrets, rather than a new account/session system. A page lock is client-side cleanup, not server-side token revocation. Document how credential rotation or mode changes close open streams and invalidate detailed access; if expiry or live revocation is required, define and review that mechanism before promising it. Protect the dashboard transport with operator-configured HTTPS; a bearer credential over plain HTTP is exposed on that connection.

## Explicit control of external requests

- Add an operator-controlled global prohibition on optional internet requests, overriding per-feature preferences. Keep configured Bitcoin RPC functional, including any DNS/TLS needed for that selected connection; this is not a promise that the process has no network activity. Define the policy scope as the four optional server features below, not arbitrary browser or operating-system traffic.
- Provide separate controls for peer GeoIP lookups, dataset downloads, application-release checks, and reachability probes. Show the effective policy clearly, and keep management changes authenticated.
- Enforce policy before scheduling, dispatch, retries, redirects, and manual updates. Use feature-owned abort controllers and policy generations rather than aborting the shared runtime controller, which also owns Bitcoin RPC and SQLite lifetime. When runtime policy disables work, cancel relevant in-flight optional requests and prevent old completions/retries from scheduling more calls. Apply validated, persisted preference changes coherently with cancellation and effective-policy reporting.
- Continue local SQLite hydration and pending local persistence when outbound traffic is denied. A fully downloaded, validated dataset may finish its local merge under the existing timestamp arbitration; disabling network traffic does not undo an already committed write. Cancel incomplete downloads and clean their exact temporary files. Manual dataset updates must return a clear disabled/skipped result without connecting.
- Distinguish an intentionally disabled probe/provider from proven healthy or failed connectivity. Do not produce repeated outage notices for an operator-disabled feature.
- Existing documentation/repository/block-explorer links are user-initiated browser navigation, not background requests; identify that distinction rather than promising that a server-side switch blocks browser navigation. Continue to serve dashboard assets locally and do not embed third-party images/URLs returned by a provider.

## HTTPS provider support

- Isolate provider transport, response adaptation, quota handling, and safe error reporting from local hydration and persistence.
- Offer local/database-only operation and an explicitly selected HTTPS-capable provider. Keep credentials server-side, validate TLS, prohibit downgrade redirects and automatic HTTP fallback, and cancel on policy changes. Verify each redirect before following it; never forward a key to a different origin. Use reviewed fixed provider endpoints and public IPv4/IPv6 literals only, preserving current private/reserved/onion/I2P/CJDNS/non-IP exclusions; do not add arbitrary provider URLs or hostname resolution as part of this change.
- Treat the existing free HTTP provider as an explicitly identified legacy choice, with a visible transport/disclosure explanation. Do not silently send peer addresses to a different company.
- ip-api Pro is a paid candidate with HTTPS and the existing field family. Verify the chosen endpoint/field mapping with fixture responses before claiming adapter compatibility. The [official service](https://members.ip-api.com/) advertises HTTPS; its [authentication FAQ](https://members.ip-api.com/faq) specifies a key in a GET query parameter. That makes URL/error/log sanitization essential: a key must never appear in logs, public configuration, browser responses, or error details. Configure it through the existing mounted-secret approach and require an operator-supplied subscription/key; none is selected or purchased by this plan.
- ipwho.is is another HTTPS-capable candidate without a free-endpoint API key. As reviewed, its [official documentation](https://ipwhois.io/documentation) specifies 1,000 free requests per day per client IP, HTTP 429 with `Retry-After` until reset, no free security/currency data, and no free SLA. Its nested field structure differs from the current response. Preserve missing classification information as unknown rather than inventing false/residential guarantees. The existing 1.5-second pacing alone cannot protect a daily quota; define a provider-specific budget/reset policy, including restart behavior and quotas shared by deployments behind the same public IP.
- Retain old cached data and provenance. A different provider requires explicit source metadata in adapters, persistence, schema/type contracts, and UI before it can be enabled; the current save path hardcodes `ip_api`. Review how unknown security fields survive SQLite, peer normalization, table/export output, hosting aggregates, and scoring. Do not silently coerce unknown into false, relabel old records, or discard useful local locations.
- HTTPS protects transport, while the selected provider still sees the queried peer address and requesting server address. No retention/anonymity promise is inferred from HTTPS or a free tier; document that disclosure and review the chosen provider's current privacy terms before enabling it.

## Decisions to confirm before implementation

1. Exact aggregate allowlist and redacted public presentation, including small-count inference; defaults for new installations and older configurations without an explicit viewing mode.
2. Initial HTTPS provider, if any: ip-api Pro with an operator-supplied key, another provider with a reviewed response adapter and quota policy, or local-only operation. Approve any API/UI/persistence change needed to represent unknown classification fields.
3. Provider and outbound-control defaults for upgrades and new installations, so transport/privacy improvements do not silently change destination, cost, or expected connectivity. A proposed privacy-oriented new-install default denies optional outbound work until configured; this proposal is not an enacted migration or default.
4. Whether shared viewing credentials with documented rotation/restart behavior are sufficient, or viewing sessions need expiry/live revocation. Choose the deployment HTTPS boundary and secret provisioning before enabling private viewing.

Opening this planning draft does not authorize a provider subscription or change any deployment policy.

## Acceptance tests and validation

- Exercise anonymous, viewer, and administrator identities in every viewing mode across all monitoring routes, both peer response forms, HEAD, errors, conditional responses, and direct streams. Viewer credentials must never authorize mutations.
- Inspect serialized public responses and browser network payloads for forbidden fields. Inject sentinel addresses, paths, credentials, precise coordinates, and extension fields; none may cross the redacted boundary.
- Verify private polling does not begin before authentication. Cover login errors, locking, private-data cleanup, reload, stream reconnection, and the approved rotation/revocation mechanism without credential persistence. Test viewer/admin separation and valid administrator access during anonymous throttling behind direct, trusted, and untrusted proxy configurations.
- With global outbound requests denied, assert zero optional provider, dataset, release-check, or reachability calls during startup, retries, preference changes, manual updates, redirects, and recovery. Exercise disabling during each in-flight feature, re-enabling, and late callbacks. Keep configured RPC, local hydration/persistence, and an already downloaded dataset's local merge working; verify disabled reporting never falsely claims successful probing.
- Test HTTPS success, TLS errors, HTTP downgrade/cross-origin redirects, malformed and application-level failure responses, provider-specific quota/reset behavior, disabling/cancellation, and secret-safe diagnostics. Include credential sentinel strings in fetch errors and redirect targets, absent security fields through persistence/API/UI/export, source migration, and rejected private/non-IP hosts. Use fixtures/local HTTPS test servers, never real credentials or billable provider requests.
- Run syntax/type/generated-contract checks, backend and frontend suites, Chromium/Firefox/WebKit privacy/security coverage, Compose configuration tests, and production-container checks for the eventual implementation.

Preserve native Node 26 execution, zero production npm dependencies, and existing runtime safeguards. The separate local hydration planning draft can proceed without choosing a provider or implementing viewing modes; coordinate its worker cancellation and timestamp-winner rules before adding runtime outbound policy. Implement this privacy work in separately reviewable steps for read authorization/redaction, outbound controls, and the operator-selected provider adapter, with contract/UI updates preceding any incompatible provider activation.

This draft adds only this document. No access policy, provider, configuration, UI, or acceptance tests are implemented or claimed as passing here.
